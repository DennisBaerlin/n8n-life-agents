# Referenz zu `packages/core/CLAUDE.md` — Mechanik der Core-Registries, Tabellen und Functions

On-demand lesen; **keine Regeln** (die stehen in `packages/core/CLAUDE.md`). Spalten/CHECKs sind 1:1 in `packages/core/db/*.sql`, fn-Verträge in `docs/fn_catalog.md`; diese Datei erklärt das Zusammenspiel.

## Advisor-Plaene (`agent.advisor_plans`)

Persistenz der Berater-Agenten (`finance_advisor` mit `domain='finance'`, `career_advisor` mit `domain='career'`). Spalten: `domain` (text, Pflicht, kein Default; leer → `{ok:false}`), `person_id` (text, NULL=Haushalt; FK → `agent.persons` ON DELETE RESTRICT), `plan_name`, `status` (`draft|active|superseded` CHECK), `version`, `interview_state` (jsonb: `{section_key: {content, data, saved_at}}` — `section_key` ist freier Text, der Katalog ist Prompt-Daten), `plan_md`. Genau ein `draft` und ein `active` pro `(domain, person_id)` (Partial-UNIQUE-Indizes `NULLS NOT DISTINCT`) + `UNIQUE NULLS NOT DISTINCT (domain, person_id, version)` (db_test `test_advisor_plans_person_keying`). Person-Scope registry-getrieben (`core.context_scopes` des Plan-Contexts): household (finance/`financial_planning`) → `person_id` NULL; per_user (career/`career_planning`) → reale `person_id` aus `agent.fn_resolve_sender(chat_id)`, Prosa-Doc suffigiert. Owner-Anker via `agent.fn_owner_person_id()` (LIMIT 1, RAISE-frei — eine Quelle für read_plan-Fallback/Review/refresh_market_signals/Migration). `updated_at` via `agent.touch_updated_at()`.

- Functions: `fn_advisor_save_section` (Sektion in den Draft, `version = MAX+1` je `(domain, person_id)`), `fn_advisor_publish_plan`, `core.fn_advisor_read_plan(text, text)` (domain + chat_id; per_user ohne chat_id → Owner-Fallback). Alle drei lösen scope/`person_id` aus der Registry + `fn_resolve_sender`; per_user ∧ unaufgelöster Sender → `{ok:false}`; Permission via `fn_check_write_permission`. Publish supersedet den bisherigen `active` der `(domain, person_id)` (Versions-Audit, nie gelöscht) und upsertet das Domänen-Plan-Doc — Context-Name aus `core.advisors.plan_context` (finance → `financial_planning`, career → `career_planning`), per_user suffigiert `<base>__<pid>` (lazy, `agent_name=NULL`, `managed_by='agent'` → vom Seeder nie überschrieben, `package`=Domain). Publish komponiert die `section_data` block-weise zu `metadata.facts` und prüft vor jedem Write, dass jeder Top-Block (`goal`/`risk_profile`/`target_allocation`/`glidepath`/`emergency_reserve`) von genau einer Sektion kommt (der `jsonb_each`-Merge ist storage-order → eine Doppelung verlöre still eine Hälfte). Tests: `test_fn_advisor_save_section.sql`, `test_fn_advisor_publish_plan.sql` (inkl. finance_ro-Negativtest).
- **E2E-Sentinel:** der Advisor schreibt unter `domain='__e2e_finance__'`, wenn die `chat_id` mit `test_e2e` beginnt — `fn_clear_e2e_data` räumt `advisor_plans` (`plan_name LIKE`/`domain ILIKE` Sentinel) und agent-publizierte Sentinel-Context-Docs (`name ILIKE` Sentinel und `managed_by='agent'`); das Chat-Memory der `test_e2e…`-Session leert der E2E-Treiber je Case (`Clear-ChatSessionMemory`, `scripts/dev/test_n8n_state.ps1`).

## Trigger-Monitoring (`agent.monitor_*`)

- **`agent.monitor_triggers`**: eine Zeile = ein Trigger. `domain` (default `general`), `label` (UNIQUE je (domain, lower(label)) — Trigger sind Config, kein Ledger, das set-Tool braucht deterministische Label-Auflösung), `trigger_type` (`threshold|drawdown|date|recurring_info`), `acquisition_method` (Core-Builtins `web_search|sql|none` + Paket-Methoden aus der Registry `core.monitor_acquisition_methods`, FK; Block/Verträge → `docs/package-contract.md` §3.9) + `acquisition_spec` (jsonb), Vergleich (`comparator gte|lte`, `threshold_value`, `drawdown_pct` 0..100, `reference_value` = Trailing-Peak-Ratchet, `due_date`, `warn_days_before`), Validierung (`expected_unit` — Pflicht bei web, `min/max_plausible`, `max_jump_pct`), Cadence (`check_interval INTERVAL`, `next_check_at`, `last_checked_at`), Zustand (`status armed|fired|disabled`, `fired_at`, `last_value`, `fail_streak`). CHECKs: Typ×Feld-Konsistenz; Web-Rate-Limit `check_interval >= 12h` bei `web_search`; Spec-Shape je Core-Methode (Paket-Methoden: BEFORE-Trigger `trg_monitor_triggers_validate_spec` → Paket-`validate_fn`, nur bei INSERT/UPDATE OF method/spec); Bounds-Sanity. GRANT SELECT an `core_ro` + `GRANT core_ro TO current_user` (für den in-fn `SET LOCAL ROLE`-Switch). **Parken:** ein Trigger einer nicht verfügbaren Paket-Methode (`agent.fn_monitor_method_status`) wird vom Heartbeat übersprungen — kein `fail_streak`, kein Alarm. `package` (text NOT NULL DEFAULT `'core'`, additiv Init-only) = Lifecycle-/Purge-Owner (Kubernetes-ownerReference); `fn_pkg_purge_data` räumt `WHERE package=<pkg> AND origin='user'`.
- **`agent.monitor_observations`**: Audit-Log jeder Wert-Beschaffung (auch dirty: `ok`, `value`, `unit`, `as_of`, `source_url`, `reason`); FK `ON DELETE CASCADE`. Der Ratchet lebt als `reference_value` am Trigger.
- **Functions:** `fn_next_check`, `fn_monitor_due`, `fn_validate_observation`, `fn_monitor_acquire` (Builtins + Registry-Dispatch an die Paket-`acquire_fn`, nie RAISE), `fn_monitor_method_status`/`fn_monitor_validate_params`, `fn_monitor_probe` (read-only Test-Abruf vor dem Gate, liefert bei Paket-Methoden die Bestätigungszeile `display`), `fn_monitor_evaluate` (die atomare Auswertung: FOR UPDATE + Status-Recheck, Latch/Ratchet/Advance entscheidet die DB, Config-Knobs `monitor.*` zur Laufzeit), `fn_create/set/delete_monitor_trigger` (alle CHECKs als `{ok:false}` gespiegelt), `fn_resolve_monitor_trigger` (`p_active_only` default FALSE). Bekannte Grenze: `statement_timeout` wirkt nicht aufs innere EXECUTE der sql-Acquisition (läuft unter `SET LOCAL ROLE core_ro`). Tests: `test_fn_next_check/monitor_due/validate_observation/monitor_probe/monitor_evaluate/create|set|delete_monitor_trigger.sql` + `test_monitor_acquisition_methods.sql` (Test-Methode `zz_test`) + `test_core_only.sql`; fx-Methode: `tests/db/finance/test_fn_monitor_acquire_fx_rate.sql`.
- **Publizierte Read-Windows:** `core.fn_monitor_trigger_summary(p_domain) → (armed, fired)` (Advisor-Cron) und `core.fn_list_monitor_triggers(p_domain) → (label, trigger_type, status, spec_summary)` (der Advisor liest beim Plan-Publish die bestehenden Trigger seiner Domain; `tool_list_monitor_triggers` unter `<pkg>_ro`). Beide SECURITY DEFINER, `search_path=pg_catalog`, `REVOKE ALL FROM PUBLIC`, EXECUTE an jede `<pkg>_rw`/`<pkg>_ro` (in `fn_provision_package_roles`). Tests: `test_fn_monitor_trigger_summary.sql`, `test_fn_list_monitor_triggers.sql`, `test_role_permissions.sql`.
- **Cron vs. Trigger — Live-Vorbild:** `cron_refresh_fx_rates` beschafft + persistiert (`finance_fx_rates`; Entwickler-Artefakt, build-time, darf schreiben und Dialoge führen); ein Trigger mit der finance-Methode `acquisition_method='fx_rate'` beobachtet den persistierten Wert (Agent-Artefakt, runtime, HITL-erstellt, read-only + Alarm). Advisor-Wunsch „Beschaffung persistieren" = Vorschlag, der Entwickler baut den Cron, danach setzt der Advisor `sql`-Trigger darauf. Genau ein Scheduler-Eintrittspunkt je Rolle: n8n-Schedule-Trigger je Cron, `cron_check_triggers` als einziger Heartbeat. `http_json`-Acquisition bleibt Backlog.
- **Monitor-Core-Protection:** Spalte `origin` ('core'|'user') + `trg_monitor_triggers_protect` (BEFORE DELETE blockt core) + `{ok:false}`-Guard in `fn_delete_monitor_trigger`. Core-Seed `household_facts_freshness` (jährlich, sql-Acquisition: `SELECT core.fn_stale_facts_count()` — Count der `persons[]`-Einträge mit as_of > 12 Monate über family + household-Kontexte aktiver Pakete; EXECUTE an `core_ro`) idempotent in der Init. Kein R__-Upsert der Core-Trigger-Zeile — `fn_set_monitor_trigger` erlaubt Owner-Spec-Edits; die Logik lebt in der R__-fn.

## Haushalts-Fakten-Schicht (`core_contexts` md-first + `metadata.facts`-Sidecar)

Die Kontexte `family` (global) und `finance_profile` (advisor-scoped) tragen neben dem Prosa-`content` ein jsonb-Sidecar `metadata.facts` nur für berechenbare/kritische Felder (Skelett-Doku im Kopf von `agent.core_init.sql`).

- **Trigger `trg_validate_household_facts`** (`agent.core_init.sql`, feuert `WHEN metadata ? 'facts'` — paket-agnostisch): person_id-Regex+unique, Vor-+Nachname non-empty, role-Enum, birth_date/as_of DATE-castbar + as_of nie in der Zukunft, telegram_user_id numerisch+unique; **Derived-Key-Denylist rekursiv über alle jsonb-Ebenen jedes Sidecars**: `age/alter/current_age/start_year/retirement_year/target_year/income/projected_income/years_to_*` + Prefix `derived_/computed_` + Substring `nominal` + `regelaltersgrenze/kindergeld` werden abgewiesen (gilt auch für die block-strukturierten `financial_planning`-Plan-facts). Roh-Inputs (`birth_date/start_age/planned_retirement_age/horizon_years/target_income_eur_month`) bleiben erlaubt; Sidecar sonst open-world. Reservierte Form-Keys: `persons` = Array von Objekten mit regex-gültigem, eindeutigem `person_id`, `household` = Objekt; per_user-Kontexte tragen kein `persons`. Bidirektional: ein family-Write darf keine `persons[]`-Referenz irgendeines Kontexts verwaisen, und jede `persons[].person_id` eines Nicht-family-Kontexts muss in family existieren (FK-Analogon — jede referenzierende Zeile zählt, auch die eines inaktiven Pakets). Dazu `trg_core_contexts_protect` (BEFORE DELETE via Registry, s. u.) + `trg_core_contexts_no_truncate`/`trg_monitor_triggers_no_truncate` (Statement-Level).
- **Validator-Registry `core.context_validators`:** der generische Anteil bleibt in `agent.fn_validate_household_facts` (Trigger-gekoppelt). Paket-Strukturregeln (z. B. `finance.fn_validate_finance_profile(jsonb)`) dispatcht der Trigger `trg_core_contexts_validate_facts_fn` generisch: `NEW.name → validate_fn → dyn. EXECUTE` über den einen Helfer `agent.fn_validate_context_facts` (auch die freundlichen Vorprüfungen von `fn_set_context_facts`/`fn_advisor_publish_plan`); eine per_user-Zeile `<base>__<pid>` über den längsten per_user-Basisnamen (`agent.fn_context_base_name`), ihre Meldung ohne Werte (`check_violation`, nur Basis-Name — ein RAISE erreicht über `sub_error_notify` den Owner); ein UPDATE mit unveränderten facts wird nicht neu geprüft (search_path=`pg_catalog`; `to_regprocedure`-Guard → fehlt die Zeile, entfällt der Dispatch still). Das Paket deklariert die Bindung nur im `manifest.json` (`context_validators`), der Host (`seed_data.sh`) upsertet own-schema-scoped (`validate_fn` muss `<pkg>.*` sein); Paket-Rollen können die Registry per D10 nicht schreiben. PK = ein Validator je Context.
- **Render-Registry `core.context_renderers`** (`core_contexts.name → render_fn(text) + package`): `core.fn_fetch_context` (SECURITY DEFINER) dispatcht generisch (`to_regprocedure(…(text))`-Guard) und wrappt uniform `Banner + Header + _meta-Stempel + '---' + Prosa-content`. Die `render_fn` liefert nur den Header (Ableitungen render-at-fetch), NULL ⟹ roher content. Signatur `fn(text)→text`; der Core bindet `agent.*` nur für `family`, der Finanzprofil-Renderer ist `finance.fn_render_finance_profile` (joint cross-context family unter dem DEFINER `fn_fetch_context`). Ein Render-Pfad für alle Contexts; `metadata.render_fn`-Flag retired.
- **Advisor-Registry + Engine `core.advisors`** (`domain PK → plan_context + review_fn + advisor_agent + package`): die generische Core-Advisor-Engine gleicht den publizierten Plan (Soll, `financial_planning.metadata.facts`) gegen die Ist-Welt ab. Tunbare Skalare in `core.config` (`schedule.drift_check`/`plan_review`, `model.advisor_review`, `cron_enable.*`, `advisor.drift_pace_pp`/`plan_stale_days`), keine Modell-Kopplung in der Registry. Manifest-`advisors`-Block verschachtelt `{domain:{plan_context,review_fn,advisor_agent,learn_notes?}}` (`learn_notes` = das Plan-Dokument darf owner-bestätigte Lern-Notizen tragen, nur household-Plan-Kontexte, contract_lint 16c); `review_fn` muss `<pkg>.*`; `fn_pkg_purge_data` räumt advisors und context_renderers mit.
  - **Geteilte Notify-Dedup-Schicht `core.notification_state`** (`core.notification_init.sql`, `PK (source, key)`, `state ok|fired`, `last_fired_at`, `expires_at`): eine „schon-gemeldet?"-Adresse aller Owner-Benachrichtigungs-Producer (Alertmanager-`nflog`-Muster). ## Multi-User-Pairing (`agent.pairing_state`)

Identity-Bootstrap: verknüpft eine numerische `telegram_user_id` (BIGINT; nie Username — OpenClaw-CVE GHSA-mj5r-hh7j-4gxf, Identity-Rebinding) mit einer Haushalts-`role` (owner|partner|child). Race-festes Single-Use-Challenge-Muster (`FOR UPDATE SKIP LOCKED`, Exakt-Match, Expiry, Bindung, `consumed_at`-Replay) mit `role` + `fail_count`-Lockout.

- CHECK/Partial-UNIQUE: `role`-CHECK · Entropie-Boden `challenge ~ '^[A-Za-z0-9]{8,}$'` (≥8 alphanum ~47 bit; OWASP: <64 bit ⟹ Rate-Limit/Lockout) · `fail_count >= 0` · Partial-UNIQUE `(telegram_user_id) WHERE consumed_at IS NULL` · Partial-UNIQUE `(role) WHERE consumed_at IS NULL AND role='owner'` · Partial-UNIQUE `(person_id) WHERE consumed_at IS NULL AND person_id IS NOT NULL` (eine offene Member-Einladung je Ziel-Person) · CHECK `pairing_claimed_together`. Stage-Spalten: `person_id` (Einladungs-Ziel, NULL beim Owner-Bootstrap) · `claimed_uid`/`claimed_chat_id`/`claimed_at`. Der owner-no-rearm-Guard liest cross-table und lebt in `fn_arm_pairing_challenge`: er blockt nur einen gepairten Owner (`role=owner` mit `telegram_user_id`), nicht das Bootstrap-Skelett.
- Functions: `fn_arm_pairing_challenge` (supersedet offene Challenges desselben Ziels; `person_id`-Param für Member-Einladungen), `fn_consume_pairing_challenge` (Owner-Bootstrap: löst ein + bindet sofort), Merge-Kern `fn_merge_member_identity(person_id, uid, role)` (liest die aktuelle `telegram_user_id` der Zielperson vorab → Doppel-Bind/Replay = `{ok:false, already paired}` bzw. `{already:true}`; beide Bind-Pfade rufen ihn). Einladungs-Flow: `fn_claim_pairing_challenge` (Member löst ein → stagt, bindet nicht) · `fn_confirm_pairing(id)` (Owner ✅ → commit, idempotent) · `fn_reject_pairing(id)` · `fn_check_household_invite`/`fn_invite_household_member` (owner-only Einladung im Chat). Der Bind mergt nur `telegram_user_id`+`role` in eine bestehende `family`-Person → `fn_validate_household_facts` bleibt Backstop. `pairing_state` ist ephemer → nicht im Backup.
- Orchestrator-Wiring: der Pre-Router (`packages/core/build/workflows/agent.orchestrator.ps1`) löst `from.id` per `fn_resolve_sender` vor dem LLM auf (Telegram-Allowlist `*` → die DB ist die Allowlist); `/start <code>` eines Unbekannten → `fn_consume_pairing_challenge`, sonst Knock → Owner-Notify, gedrosselt über `fn_register_knock` → `core.fn_should_notify(source='knock')` (Default 1h). Owner-Skelett-Seed: `packages/core/db/util/util_seed_owner_skeleton.sql` (PII via psql-Variablen), aufgerufen von `provisioning/lib/bootstrap_owner.sh`, das danach `fn_arm_pairing_challenge(role=owner)` armiert (Code nur ins Terminal). Member-Einladung: Guide-Tool `tool_invite_household_member` (Deep-Link `t.me/<bot>?start=<code>`) → `/start <code>` → `fn_claim_pairing_challenge` → Owner-Notify mit `inline_keyboard` (✅/❌) → Owner-Tap (`callback_query`, `from.id==Owner`) ruft `fn_confirm_pairing`/`fn_reject_pairing`. Der Orchestrator trennt `message` vs `callback_query` direkt hinter `Trigger normalize`.

## Entscheidungen (bei uns anders — belegt)

- `managed_by` (core_contexts) und `origin` (monitor_triggers) bleiben zwei Namen für zwei Achsen (Sync-Ownership vs. Authorship).
- Household-Kontexte entstehen ausschließlich als Installer-Skelett, nie Insert-on-first-write (die Sichtbarkeit `agent_name` ist paket-deklariert; ein Insert machte sie still global).
- Bidirektionaler Referenz-Schutz als FK-Analogon über alle referenzierenden Zeilen, nicht als Registry-Filter.
- Restore form-getrieben statt registry-getrieben (das Bundle ist Daten).
- Kein R__-Upsert der Core-Monitor-Trigger-Zeile (Owner-Spec-Edits bleiben erhalten).
- Onboarding-Status als `text + CHECK` statt Cross-Schema-ENUM (ENUM-Cast scheiterte still unter `finance_rw`); Paketschlüssel → Tabelle per Konvention, keine Registry.
- Block-Liste als eigene Tabelle, nicht als Spalte auf der Knock-Dedup.
- `cron_labels` = nur noch die Toggle-Mitgliedschaft (die Texte stehen seit Textkatalog Phase B im Katalog `<pkg>.cron.<key>.*`; die fn bleibt rein `{ok,key,enabled}`).
- Attachment-Routing über den opaken Marker, nie über Inhalts-Vorklassifikation (PII-Datenminimierung: Inhalte sieht nur das Extraktions-Tool des Empfängers).
- Mini-App über die bestehenden `/webhook/*`-Pfade statt eines eigenen `/app/*` mit Datei-Dienst (arch-challenge 2026-10-27): der Proxy läuft oft auf einem anderen Rechner, ein eigener Pfad bräuchte dort einen Datei-Dienst samt Firewall-Freigabe; Actual/Firefly als Oberfläche verworfen (eigene Wahrheit + Sync). Rückfall-Trigger: der Telegram-Client zeigt die Seite im n8n-Sandkasten nicht.
