# Referenz zu `provisioning/CLAUDE.md` — Installer-Mechanik, Install-UX, Runtime-CLI, Entscheidungen

On-demand lesen; **keine Regeln** (die stehen in `provisioning/CLAUDE.md`). Jedes Skript trägt seinen Kopf-Kommentar; der Vertrag für Pakete steht in `docs/package-contract.md`.

## Topologie und Ablauf von `provision.sh main()`

Drei Schichten: der Wegwerf-Bootstrap-Launcher `install.sh` (resolve/fetch/verify/delegate, self-contained) startet den internen Applier `provision.sh`; Updates laufen über die Runtime-CLI `lifeagents update` (lädt selbst + startet den neuen `provision.sh`). `main()` ist der Erweiterungspunkt. Bundle = Metapackage: `main()` installiert erst den Core bare (`apply_schema core` + `SEED_PKG=core seed_data` + `register_package core active`), dann jedes gebündelte Nicht-Core-Paket über denselben per-Paket-Install-Pfad (`pkg_install_one <pkg>`). Kein Reverse Proxy wird installiert (bring-your-own; der Installer gibt die Proxy-Konfiguration aus).

**Haushalts-Zeitzone (ein Fakt `HOUSEHOLD_TIMEZONE`, core.env):** `resolve_household_timezone` (in `derive_network_config`) löst Env/`--unattended`-Datei > core.env > `Europe/Berlin` auf. Die Container-Zeitzone zählt nie, weil LXC-Vorlagen auf UTC stehen. Der Wert wird gegen `/usr/share/zoneinfo` geprüft und persistiert. Abgeleitet sind n8n `GENERIC_TIMEZONE` (Zeitpläne) und die Sitzungs-Zeitzone der App-DB (`install_pg.sh apply_db_timezone`: `ALTER DATABASE n8n SET timezone`, nur bei Abweichung laut `pg_db_role_setting`, dann n8n-Neustart über `PG_TZ_CHANGED`). Daran hängen `CURRENT_DATE`, `::date` und `core.fn_today()`. ALTER DATABASE statt ALTER ROLE, weil die Werkzeug-Credential dieselbe Rolle nutzt wie n8n; n8n verträgt es (seine Zeitspalten sind `timestamptz`). Ein Bestand ohne Eintrag stellt beim Update auf Berlin um (Owner-Entscheid 2026-10-23).

## Owner-Bootstrap (`bootstrap_owner.sh`)

Läuft in `main()` nach `apply_schema` und vor der API-Key-gegateten Credential-/Workflow-Injektion. Vier idempotente Schritte:

- **Owner-Setup + n8n-API-Key** über n8ns internen Setup-Flow: `POST /rest/login` (falls der Owner existiert; sonst `POST /rest/owner/setup` mit `firstName`/`lastName`/`email`/`password`) → Cookie → `POST /rest/api-keys`. Versions-stabil (der Pfad des Setup-Assistenten). Override-first (`N8N_API_KEY` aus Env oder `/etc/lifeagents/core.env` → reuse, keine dangling Keys), persistiert per-Key (`env_upsert`, kein Whole-File-Clobber) in `/etc/lifeagents/core.env` (640 root:n8n; kein n8n-Config, nur Idempotenz-State). Resilient: jeder Fehlschlag → warn + skip (Deploy fällt sauber aus).
- **RO-Lese-Credentials (`_provision_ro_secrets`, host-only):** setzt den Host-Lese-Rollen `core_ro`/`context_ro` (von `apply_schema` als LOGIN ohne Passwort angelegt) über `provision_role_password` (common.sh: würfeln → `ALTER ROLE … PASSWORD` → `core.env`-Upsert → override-first-Reuse) ein Passwort + exportiert `CORE_RO_PASSWORD`/`CONTEXT_RO_PASSWORD` für `inject_credentials`. Die Paket-Rollen `<pkg>_rw/_ro` mintet `pkg_install_one` Stufe 4 in `/etc/lifeagents/<pkg>.env`.
- **Telegram-Basis:** `setMyCommands` rollen-skopiert (`_set_bot_command_menus` in `deploy_workflows.sh`, aus den `commands`-Blöcken von core + allen aktiven Paketen; `refresh_bot_command_menus` nach jedem Paket-Statuswechsel): Owner-Befehle via `BotCommandScope{type:chat,chat_id:OWNER}`, Default-Befehle via `{type:default}`; je Scope per `getMyCommands` verifiziert. Owner-chat_id via `_resolve_owner_chat_id`; Sentinel `0`/leer = noch nicht gepairt → Owner-Scope übersprungen, beim nächsten `lifeagents update` nachgeholt. + `deleteWebhook` (`drop_pending_updates`).
- **Owner-Person-Skelett:** `packages/core/db/util/util_seed_owner_skeleton.sql` (nur die family-Zeile, `ON CONFLICT DO NOTHING`; das leere `finance_profile` legt das finance-Paket per `context_skeletons` selbst an). Struktur getrackt, PII via psql-Variablen (`OWNER_FIRST_NAME`/`_LAST_NAME`/`OWNER_BIRTH_DATE`).
- **Owner-Pairing-Code** armiert nicht mehr der Bootstrap (er stand mitten im Lauf und war bis zum Ende abgelaufen): `_arm_owner_challenge <code>` ist der Baustein; Anzeige + Warten macht das geführte Ende (`lib/owner_connect.sh`). `/start <code>` → Orchestrator-Pre-Router bindet `role=owner`. Dev/Test: die Tier-Treiber pairen deterministisch in der Container-DB (`Set-OwnerTelegramPairing`); unattended wird nie ein Code armiert.

## Schema + Workflows + Credentials

- **`apply_schema.sh`** (bash-Reimpl von `db_apply.ps1`): als postgres-Superuser (runuser, Peer-Auth) im Flyway-3-Phasen-Modell in einer psql-Session, `ON_ERROR_STOP=1`: (1) Baseline-Inits (`schema_version` zuerst, `ai_models` vor `core.config`, Rest nach Dateinamen — Belt-and-Suspenders, die Inits sind order-tolerant) → (2) `V{NNN}__*.sql` (`_emit_migration`) → (3) `R__*.sql` (`_emit_repeatable`) → (4) util (`util_{harden,create_core_ro,create_context_ro}.sql` + Laufzeit-Grants). Host-Rollen: der n8n-Owner (`install_pg.sh`, legt auch die App-DB an — immer UTF-8, Regel → `provisioning/CLAUDE.md` *Harte Regeln*) + `core_ro` + `context_ro`; Paket-Rollen legt der per-Paket-Install via `core.fn_provision_package_roles` an. Migrations-Mechanik → `docs/reference/packages.md` *Migrations-Modell*.
- **`inject_credentials.sh`** (REST `POST /api/v1/credentials`, host- vs. paket-skopiert): die CLI `import:credentials` ignoriert die JSON-id → die Workflows referenzieren Credentials über Platzhalter `__CRED_*__`; inject legt die Creds nur an (autoritativ), die Platzhalter→id-Auflösung macht `deploy_workflows` per Name-Auflösung. Eine Platzhalter↔Name/Typ-Map (`_cred_host_placeholder_names`/`_cred_pkg_placeholder_names`): `inject_credentials` legt die 7 geteilten Host-Creds an (Postgres write/`core_ro`/`context_ro` + Telegram/Gemini/Anthropic/Header-Auth — keine Paket-Literale, Naht-Guard-gelintet); `inject_package_credentials <pkg>` legt die 2 engen `Postgres <pkg>_rw/<pkg>_ro` plus die Manifest-`credentials` an (`_inject_manifest_credentials`, §3.8; data-Assembly je Typ in `_cred_assemble_data` — httpCustomAuth[qs]/httpHeaderAuth, unbekannter Typ `die`; alle env-Keys da → staged, sonst optional skip / required fail-fast). Secrets Prozess-Env override-first, sonst `/etc/lifeagents/<pkg>.env`; fehlendes Secret → Credential übersprungen. **ID-stabiler Upsert:** bestehende id per `GET /api/v1/credentials` (name+type, fail-closed — ein GET-Fehlschlag bricht ab, damit „leer" nie als Erstinstall fehlgedeutet wird) oder bei echtem Erstinstall frische 16-char-id; alle als ein Array mit einem `n8n import:credentials` upserten (hält die id bei id-Match in-place, n8n-PR #5231; der Secret wird frisch geschrieben, nie adoptiert). Als `runuser -u $N8N_USER` + gesourcte `n8n.env`, kein `--userId`. Eine stabile id wird nie gelöscht → kein Geister-Cron → kein Deploy-Restart. (PATCH/{id} wäre gleichwertig — nicht gebaut: CLI empirisch bewiesen + Parität zu `import:workflow`.) HTTP-nahe Credentials brauchen ggf. den `allowedHttpRequestDomains`-Workaround (Memory `n8n-gemini-key-split`). **Sofort-Validierung:** jede Credential nach dem Import per `POST /credentials/{id}/test` (`{status:OK|Error}`) → ein falscher Key fällt sofort als Warnung auf; non-fatal.
- **`deploy_workflows.sh`** (CLI `import:workflow --separate`, nicht REST-POST; paket-skopiert — `deploy_workflows core` deployt alles, was keinem Nicht-Core-Paket gehört [Wortgrenze-Prefix aus `provides.agents`], `deploy_workflows <pkg>` nur dessen Workflows): `import:workflow` behält die id (REST-POST vergäbe neue → das `executeWorkflow`-Referenznetz risse). Pro Workflow jq-Patch: Credential-Remap per Name-Auflösung (`_build_cred_remap` gegen `GET /credentials`) + Zeitplan-Platzhalter `__CFG_SCHEDULE_<KEY>__` → Wert aus `core.config` (`_schedule_placeholder_map`, `jq --argjson`; Rest-Platzhalter `__CFG_*` → `die` bevor live etwas geändert wird) + `__OWNER_CHAT_ID__` → reale chat_id (`_resolve_owner_chat_id`: family-Facts → `OWNER_CHAT_ID`-env → `0`; das geführte Ende deployt nach dem `/start` neu) → **laufende Auslöser abmelden** (`_deactivate_live_triggers`: jeder live aktive Workflow des Deploy-Sets mit eigenem Auslöser [jq `_WF_OWN_TRIGGER_JQ`] per REST `POST /workflows/{id}/unpublish`) → Import als n8n-User → alle per REST `POST /workflows/{id}/publish` (Fixpunkt). **Nur Geänderte:** `import:workflow` vergibt jedem importierten Workflow eine neue versionId, setzt ihn unpublished und meldet einen Telegram-Trigger ab — auch bei gleichem Inhalt (n8n 2.44.4 `import.service`). Darum steht je Workflow in `/var/lib/lifeagents/workflow_deploy.state` (`WF_DEPLOY_STATE_FILE`) `<id>\t<fingerprint>\t<versionId>`; Fingerabdruck = sha256 der gepatchten Datei + Deploy-Kontext (n8n-Version aus `package.json`, `WEBHOOK_URL`, sha256 des Bot-Tokens). Abmelden + Import nur, wenn Fingerabdruck neu/anders, live fehlend oder live-versionId ≠ gespeicherte (am Server geändert/DB zurückgespielt); unverändert + unpublished → nur publish; sonst nichts — außer Telegram-Trigger-Workflows: die werden immer ab- und wieder angemeldet, weil `bootstrap_owner::_wire_telegram` bei jedem Installer-Lauf den Bot-Webhook löscht (Review-Fund: ohne das wäre der Bot nach einem Update ohne Workflow-Änderung taub). Eingetragen wird erst nach dem Publish und nur bei neuer versionId (ein still gescheiterter Import wird beim nächsten Lauf wiederholt). Live-Liste nicht abrufbar oder `LIFEAGENTS_DEPLOY_FULL=1` → alles wie früher; `--purge-data` löscht den Zustand. Kein Deploy-Restart: id-stabile Credentials + Abmelden vor dem Import (belegt an n8n 2.21.7, auf 2.44.4 beibehalten: `import:workflow` läuft in einem eigenen Prozess und meldet den im laufenden n8n registrierten Auslöser nicht ab). Sicherheitsnetz: lässt sich ein Auslöser nicht abmelden → ein Neustart am Ende; scheitert der Import → die deaktivierten Workflows werden mit altem Stand reaktiviert. Der Telegram-Webhook wird beim Deaktivieren gelöscht und beim Aktivieren neu gesetzt; Nachrichten dazwischen hält Telegram vor. Der Uninstall-Restart in `pkg_teardown.sh` bleibt (echte In-Memory-Waise).
- **`retire_workflows <scope>`:** nach Import + Aktivierung löscht `deploy_workflows` die im Manifest-Block `retired_workflows.list` des besitzenden Pakets genannten ids (explizite Tombstones, dpkg-`rm_conffile`-Analogon): GET + Namensabgleich, 404 = schon weg, nie eine id des aktuellen Deploy-Sets; Helfer `n8n_delete_workflow` (common.sh). Hatte ein gelöschter Workflow einen eigenen aktiven Auslöser → ein n8n-Neustart (#21770). Läuft nach dem Import (`contract_lint` 16e). **`retire_credentials <scope>`:** Manifest-Block `retired_credentials.list[{name, type, env_keys[], since}]` — löscht nur bei gleichem Name und Typ, streicht genau die gelisteten `env_keys` aus `/etc/lifeagents/<pkg>.env`; `contract_lint` 16f. Beide laufen auch, wenn ein Paket keine Workflows mehr im Baum hat. Einstieg `retire_stale` (Workflows → Credentials → höchstens ein Neustart zuletzt; `/healthz` meldet gesund, bevor die REST-API antwortet).
- **API-Key-Gate:** Credential-/Workflow-Deploy läuft nur mit `N8N_API_KEY` in der Env; Schema/Seed sind immer live. `N8N_URL` ist lokal `http://127.0.0.1:$N8N_PORT` (extern muss der Proxy `/api` blocken).

## Daten-Seed (`seed_data.sh`)

`seed_data()` (nach `apply_schema`, postgres-Superuser, eine psql-Session) ist der Seeder (Dev/Test wie Prod): `ai_models.json` → `agent.ai_models` (zuerst) → `.config`-Blöcke aller Manifeste (`_seed_package_config` → `core.fn_config_seed`, conffile-Semantik §3.6) → `capabilities_catalog` (`managed_by='build'`, aus Kopf + Fragmenten von core + aktiven Paketen komponiert; `refresh_capabilities_catalog` nach jedem Statuswechsel; zusammen mit `installed_packages`) → `packages/*/contexts/*.md` (`managed_by='seed'`, `package=<pkg>`). Danach die paket-generischen Seeder: `_seed_context_validators`, `_seed_context_scopes`, `_seed_protected_contexts`, `_seed_onboarding_sections` → `<pkg>.onboarding_state`, `_seed_services` → `core.services` (`provides.services` → alias→`workflow_id`+`package`, id aus den getrackten Workflow-JSONs via `_collect_workflow_name_ids`; Core = String-Form, Nicht-Core-Tool-Services = Objekt-Form `<pkg>:<alias>` + `permission` + `description`, CHECK `services_name_package_check`). Namens-Standard: `seed`=Daten-Zeilen, `emit`=SQL-DDL-Treiber, `register`=Paket-Status-Registry.

- **Seed-Conffile-Guard:** `_seed_context_md` upsertet mit `ON CONFLICT … DO UPDATE … WHERE core_contexts.managed_by <> 'agent'` — eine vom Owner/Agenten übernommene Zeile wird vom Re-Seed nie überschrieben (protected_contexts schützt nur vor DELETE). Bewahrte Zeilen werden per NOTICE gezählt. Das `.dpkg-dist`-Äquivalent (Owner-Signal bei geändertem Paket-Default) ist DEFER → BACKLOG.
- **Fakten-Skelette** (`_seed_context_skeletons`, Manifest-Block `context_skeletons`): insert-only, nur bei registriertem Paket, auch mit `--no-seed` → heilt `finance --purge` + Neuinstallation.

## Install-UX

- **`ui_*`-Schicht (`common.sh`):** `ui_section` (benannter Banner ohne Zähler) · `ui_box` (Ergebnis-Box auf STDOUT; Secrets via STDIN-Pipe) · `ui_input` (der Eingabe-Primitiv, maskiert bei secret) · `ui_interactive` (`/dev/tty` ∧ `${UNATTENDED:-0}`≠1) · `ui_page` (Anzeige-Text, auf einem TTY über den Owner-Pager) · `ui_color_enabled <fd>` (Farb-Prädikat je Strom). gum optional: jede Funktion hat einen gum-Zweig + plain-ANSI-Fallback; `ensure_gum` lädt das Binary SHA256-gepinnt vom GitHub-Release (Pins `GUM_VERSION`/`GUM_SHA256_*` in common.sh) nach `/usr/local/lib/lifeagents/bin/` — best-effort, nur im interaktiven Pfad; `GUM_DISABLE=1` erzwingt plain. Farb-Guard nach no-color.org; Präfixe ASCII `[*]/[+]/[!]/[x]`.
- **`ui_choose <header> <multi:0|1> [preselect]`:** der Listen-Picker der Runtime-CLI: gum-Zweig `gum choose` mit nativem `--label-delimiter=TAB` + nummerierter Plain-Fallback (yay-Muster). Optionen von STDIN als `label<TAB>value`, gewählte Values auf stdout, leer + `return 0` = Abbruch/kein TTY/keine Optionen; Echo der Wahl zeigt die Labels. Ein leerer Wert ist erlaubt und heißt „nichts gewählt" (intern `_UI_EMPTY_VALUE`, gum-`TrimSpace`-Falle). Konsumenten: Hauptmenü bei nacktem `lifeagents`, Verb-Menüs der Sub-CLIs, Ziel-Picker von `reconfigure`, Übersicht vor dem Installieren, Missing-Arg-Picker (`package install` [Multi] · `activate`/`deactivate`/`uninstall`/`reconfigure` · `config set` · `household remove|unlink|unblock` · `backup restore`); `household block` picker-los. Statusfilter je Verb-Semantik. Non-TTY/`--unattended`: byte-identisch (Args umgehen immer; Missing-Arg → Usage-`die`; nacktes Verb → Hilfetext). gum-Strg-C (Exit 130) = `ui_abort` (TERM an `$$`); ESC = „leer + return 0". `contract_lint` 12d sanktioniert `ui_choose` je Aufrufer; 12e hält die Wert-Konvention statisch.
- **Paket-Secrets-Wizard (`pkg_lifecycle.sh::_pkg_secrets_wizard`, Stage 4):** liest den Manifest-`credentials`-Block und fragt je env-Key env-override-first → Seen-Gate (`KEY=`-Zeile in `<pkg>.env`) → interaktiv (`_prompt_validated`). Assembler-Typen `httpCustomAuth` | `httpHeaderAuth`. `lifeagents package reconfigure <pkg>` = re-ask + id-stabiler Upsert. Absicherung `contract_lint` Check 12 (Schema/type-Enum · Manifest↔Workflow-Parität · Naht-Guard · Prompt-Gate-Guard) + doctor „Paket-Secrets".

## Bootstrap-Launcher + Release-Asset (`install.sh`, `lib/fetch_release.sh`, `.github/workflows/release.yml`)

- **`install.sh` = Wegwerf-Bootstrap-Launcher** (nur Erstinstallation via `curl|bash`), self-contained: Quelle auflösen (Default `/releases/latest`; `--version <tag>` pinnt), Tarball + `.sha256` anonym laden (*Download* unten), SHA256 vor dem Entpacken verifizieren (Mismatch → `die`), entpacken, `exec bash <tree>/provisioning/provision.sh "$@"`. Kein `--local`, kein Loop-Guard, keine Frage.
- **`provision.sh` = interner Applier:** kein Fetch/`--version`; aufgerufen von `install.sh`, `lifeagents update` und dem Test-Substrat. Kein Endnutzer-Einstieg.
- **`lib/fetch_release.sh`** für `lifeagents update` (nicht von `provision.sh` gesourct): `fetch_and_run_release()` löst `latest` auf, lädt + verifiziert, entpackt und exec't den neuen `provision.sh` (self-replacing, `rustup self update`-Muster). Ruft nie `install.sh`. Kleine bewusste Doppelung Bootstrap↔Runtime.
- **Release-Asset = der getrackte Install-Baum** als `tar.gz` (+ `.sha256`), gebaut von `release.yml` auf Tag `v*.*.*` per `git archive --format=tar.gz --prefix=…/ HEAD provisioning packages .gitattributes`. Die Pathspec ist die eine Quelle (`layout_lint` L6). `git archive` ist deterministisch und nimmt nur getrackte Dateien → gitignorte Secrets können strukturell nicht hinein; No-Secrets-Gate in der Action. Zusätzlich lädt die Action `provisioning/install.sh` als Asset `install.sh` hoch (stabiler Einstieg aus dem letzten Release statt aus `main`). Action nutzt `${{ github.token }}`; idempotent (`gh release create … || true` + `gh release upload … --clobber`).
- **Download — ein Weg, immer anonym** (Owner-Entscheid 2026-10-24, öffentliches Repo; der `# >>> gh-download`-Block steht byte-gleich in `install.sh` und `lib/fetch_release.sh`, `contract_lint` Check 23): kein Token, keine Frage, nie ein Auth-Header. `/releases/latest` bzw. `/releases/tags/<tag>` liefern Metadaten samt Assets (ein Lauf = 3 Anfragen; anonym 60/h je IP).
  - 404 → „kein stabiles Release“ bzw. „Tag existiert nicht“. Abfragelimit = 429 oder 403 mit `x-ratelimit-remaining: 0`. Status `000` = Netzfehler oder nach den Headern abgebrochener Download (curl-Exit ≠ 0 trotz 200) → eigene Meldung, nie „manipuliert“.
  - Status-Erfassung ohne `curl -f`, sicher unter `set -e`; Redirects (S3) nur auf https. `PROVISION_GH_API` ist nur ein Test-Override. Test: `scripts/dev/release_fetch_test.ps1` (Mock `tests/mock_github`).
  - **Altbestand:** ein `GH_TOKEN` aus der privaten Zeit in `/etc/lifeagents/core.env` bzw. `/etc/n8n/install.env` entfernt `provision.sh` (`drop_legacy_repo_token`) mit Hinweis, ihn auf GitHub zu widerrufen.
- **Endnutzer-Bootstrap:** `install.sh` als Release-Asset laden, dann als root ausführen; mit `&&` verkettet, damit kein stale `install.sh` aus dem CWD startet (nie `| bash`). `--profile` defaultet auf `release`:

```bash
curl -fsSL https://github.com/DennisBaerlin/n8n-life-agents/releases/latest/download/install.sh \
  -o install.sh && bash install.sh --domain n8n.example.com              # latest stable
# gepinnt: ... -o install.sh && bash install.sh --version v0.1.0 --domain n8n.example.com
```

- **Rückweg nach gescheitertem Update** (`upgrade_rollback_hint`): lädt das `install.sh` des NEUEN Release anonym (ein Alt-Release-`install.sh` verlangte zwingend einen Token) und installiert `--version <vorheriges Tag> --profile <bisheriges>`. Nach dem Repo-Neustart ohne Historie (v0.14.0) gibt es die Tags davor nur noch im privaten Archiv-Repo; der Rückweg dieses einen Sprungs geht nur von dort, die Datensicherung bleibt unberührt.
- **Umstieg einer Instanz vor v0.14.0:** ihre alte CLI schickt beim ersten `lifeagents update` noch den alten PAT mit (ein gültiger PAT darf öffentliche Repos lesen) → erst updaten, dann den PAT widerrufen. Ist er schon widerrufen: das neue `install.sh` anonym laden und mit dem bisherigen `--profile` ausführen (idempotenter Converge über die bestehende Installation).

- Channels: `/releases/latest` = stable; ein Testing-Strang (prerelease-Flag) ist ein Folgeschritt.

## Backup/Restore (`backup_cli.sh`)

Standard-Werkzeug `pg_dump`/`pg_restore`, CLI-only (postgres-Superuser via runuser); Klartext nur transient in `/dev/shm`.

- **Was** (je Paket, `manifest.json`-`backup`-Block): `schema_dump:true`+`exclude_tables` · `full_tables` · `filtered_tables` (`{qual→WHERE}`). Nur die Nutzerdaten-Teilmenge. `pg_dump` ignoriert `-n` sobald `-t` gesetzt ist → die CLI enumeriert alle bulk-Tabellen explizit per `-t`.
- **Bundle** = verschlüsseltes Tarball `{manifest.json (bundle_format:2, packages+versions, verify_counts), data.dump (pg_dump -Fc -a), shared.json}`, `gpg --symmetric AES256`, Passphrase = `core.backup_key('backup_encryption_key')`.
- **export** (`backup_cmd_export [pfad] [--notify-telegram]`): tmpfs-Workdir → pg_dump (`-a --disable-triggers`) + `\copy`-jsonb der gefilterten Tabellen + manifest → tar | gpg. Off-Site (`--notify-telegram`, best-effort, `_bkp_notify_telegram`): `.nla.enc` per `sendDocument` an den Owner-Chat; Token aus `core.env`, nie ins argv, `--max-time`, 50-MB-Guard, warn+skip statt `die`. Datenschutz: das Bundle bleibt im Telegram-Cloud-Speicher als Doppel-Chiffrat (gpg-Schlüssel nur offline). Auto/Cron: root-crontab-Zeile (`30 3 * * * cd /root && lifeagents backup export --notify-telegram >> …log 2>&1`); systemd-Timer ist BACKLOG.
- **restore** (`backup_cmd_restore <datei> [--yes]`) ist atomar: Decrypt+Header vor dem Wipe → Pre-Flight je Bundle-Paket gegen `core.package_registry` (fehlt → Auto-Install `--no-seed`) + Version-Gate (≠ installiert → `die` mit `lifeagents update`-Hinweis; Cross-Version nicht unterstützt) → Wipe-Übersicht → TTY-Confirm → eine `psql -1`-TX: TRUNCATE(bulk, CASCADE) + `pg_restore -a --disable-triggers -f -` (SQL-Text, läuft in der TX) + `core.fn_backup_restore_filtered(jsonb)` + Count-Verify → Fehler = Rollback. `--disable-triggers` schaltet auch FK-RI-Trigger ab → kein Topo-Sort.

## Versionswechsel (`lib/upgrade_guard.sh`)

Muster GitLab Omnibus (Auto-Backup vor jedem Paket-Upgrade, <https://docs.gitlab.com/update/package/>): n8n migriert seine Tabellen beim ersten Start einer neuen Version, zurück nur per `n8n db:revert` je Migration (<https://docs.n8n.io/hosting/installation/npm/>); n8n und alle lifeagents-Schemas liegen in **einer** DB.

- **Auslöser** (`upgrade_detect`, nach `install_base_packages`, vor `install_postgres`): installiertes n8n ≠ `N8N_VERSION`, Node-Hauptversion ≠ `NODE_MAJOR`, ein neuerer `postgresql-<PG_VERSION>`-Kandidat **oder ein Release-Wechsel** (`VERSION` ≠ `RELEASE_TAG`, beide stabile Tags; GitLab sichert vor jedem Paket-Upgrade, ein neues Release bringt nicht umkehrbare Migrationen) — und die App-DB existiert (Erstinstallation: nichts zu schützen). Oder der Merkzettel liegt noch da. Erneut anwenden (gleiches Tag, `reconfigure`) sichert nicht.
- **Ablauf:** Merkzettel `/var/lib/lifeagents/upgrade.pending` (`FROM_N8N`, `FROM_NODE`, `FROM_RELEASE` = das noch installierte Release aus `VERSION`, `BACKUP`, `KEY_TABLE`, `STARTED`) → `GET /api/v1/executions?status=running` bis 120 s abwarten (wartende Bestätigungen überleben den Stopp) → `systemctl stop n8n` → `pg_dump -Fc` der ganzen DB direkt in `gpg_sym_encrypt` (kein Klartext auf der Platte; `.part` erst bei Erfolg umbenennen) → `/var/backups/lifeagents/pre-upgrade-n8n-<alt>-<UTC>.dump.gpg` (0600). Sicherung scheitert → Merkzettel weg, n8n wieder an, `die` — nichts getauscht. Danach PG-Minor (Hold kurz lösen, `--only-upgrade`, wieder halten), Node (`nodejs=<ver>`), n8n (`npm install -g n8n@<pin>`, bei reinem Node-Wechsel `npm rebuild -g n8n`), Start, bis 15 Min auf `/healthz/readiness`; Gateway-Neustart. `upgrade_finish`, sobald der Tausch steht (n8n bereit + Gateway neu gestartet, vor dem Workflow-Deploy — das bleibt ein normaler, wiederholbarer Schritt): Merkzettel weg, nur die letzten 2 Sicherungen bleiben.
- **Abbruch:** der Merkzettel bleibt; der nächste Lauf übernimmt die Sicherung (fehlt sie und ist noch etwas zu tauschen, wird sie neu gezogen) und startet n8n + Gateway neu. `doctor` meldet den offenen Merkzettel ROT.

### Rückweg

**`lifeagents rollback`** (`upgrade_rollback`) führt den Rückweg geführt aus: Quelle = Merkzettel eines unvollendeten Updates, sonst die jüngste `pre-upgrade-*`-Sicherung samt Begleitdatei `<sicherung>.meta` (Kopie des Merkzettels, von `upgrade_prepare` geschrieben, mit der Sicherung aufgeräumt) → Zusammenfassung + Rückfrage (`ui_choose`, nur mit TTY; Daten seit der Sicherung gehen verloren, darum nie automatisch, auch nicht aus dem Chat) → Schlüssel an der Sicherung prüfen (voll entschlüsseln) → das `install.sh` des **vorherigen** Release vorab laden (Netzfehler = noch nichts geändert) → Timer + n8n stoppen → aktuelle DB nur **umbenennen** (`<db>_before_rollback`) → `gpg -d | pg_restore --create` (scheitert das: umbenannte DB zurück) → `install.sh --version <FROM_RELEASE>` mit `LIFEAGENTS_ALLOW_DOWNGRADE=1` → erst bei Erfolg die beiseitegelegte DB löschen + Telegram-Meldung. Releases vor v0.14.0 (privates Archiv-Repo) → kein Rückweg, Hinweis.

Von Hand (wenn n8n nach dem Update dauerhaft nicht startet; `journalctl -u n8n -n 100` zuerst): `upgrade_rollback_hint` druckt die Kommandos mit den echten Pfaden: n8n stoppen → Schlüssel aus `core.backup_key` lesen → `dropdb` → `gpg -d <sicherung> | pg_restore --create -d postgres` (die DB neu anlegen statt `--clean`, damit keine Tabellen der neuen n8n-Version liegen bleiben) → Merkzettel löschen → das vorherige Release über den Bootstrap-Launcher `install.sh --version <FROM_RELEASE>` (Download über die Contents-API mit dem Token aus `core.env`, nie im argv) — bewusst nicht `lifeagents update`: scheitert der Tausch, ist noch die alte CLI installiert. War der Stand kein Release, sagt der Hinweis das. Kein Schlüssel, aber ein `core`-Schema = Defekt → Abbruch (Notschalter `UPGRADE_ALLOW_NO_BACKUP=1`). Im Substrat durchgespielt (2026-10-20, v0.3.0 → Update → Rückweg): Daten zurück, n8n 2.21.7 läuft wieder — Node bleibt dabei auf 24, das alte n8n kommt damit zurecht.

## Release-Signatur (Phase 2, Owner-Entscheid 2026-10-24)

Muster Debian SecureApt: der Maintainer unterschreibt die Prüfsummenliste offline, jede Installation prüft mit `gpgv` (auf Debian vorinstalliert) gegen genau einen Schlüssel. Kein Actions-Secret (schützte nicht gegen ein gekapertes Konto), keine Sigstore-Attestation (hängt an der Workflow-Identität).

- **Schlüssel:** `scripts/new_release_key.ps1` (einmalig, Owner-Terminal, gpg aus Git for Windows, Ed25519 + Passwort) schreibt `provisioning/keys/release-signing.gpg` und `RELEASE_KEY_B64` in `install.sh` (`contract_lint` 24). Privater Schlüssel offline sichern.
- **Release:** `release.yml` baut zusätzlich `SHA256SUMS` (Tarball + `install.sh`) und legt das Release als **Entwurf** an, sobald der Schlüssel im Tag liegt. `scripts/sign_release.ps1 <tag>` (Owner-Terminal) prüft den Entwurf gegen den lokalen Tag (Tar-Strom byte-gleich mit `git archive`, sonst Blob-Hash je Datei; `install.sh` = Blob des Tags), unterschreibt detached, lädt `SHA256SUMS.sig` hoch und veröffentlicht → `/releases/latest` zeigt nie auf ein unsigniertes Release.
- **Prüfung** (`_release_fetch_verify` im gh-download-Block, also `install.sh` und `lifeagents update` gleich): mit Schlüsselbund `gpgv --keyring` über `SHA256SUMS`, dann exakt die Zeile `<sha256>  <tarball>`; ohne Bund nur bei `install.sh` eines nicht signierenden Projekts das `.sha256`-Sidecar — `lifeagents update` und `rollback` brechen ohne installierten Bund ab (Security-Audit 2026-10; Ausweg `install.sh`, das den Schlüssel eingebettet trägt). Fehlt die Signatur → Abbruch vor dem Entpacken (`reason_code signature`).
- **Schlüsselbund:** `/etc/lifeagents/release-signing.gpg`, gelegt von `install_release_keyring` nur wenn er fehlt (Erstinstallation bzw. erstes Update auf eine signierende Version = TOFU); ein Update überschreibt ihn nie (abweichender Schlüssel im Baum → Warnung). `install.sh` nimmt immer den installierten Bund, sonst den eingebetteten. Schlüsselwechsel = bewusste Handarbeit auf jeder Installation (Datei ersetzen); ein eigener Befehl dafür ist nicht gebaut.
- **Übergang:** Instanzen vor dem ersten signierenden Release laden dieses noch ohne Signaturprüfung, danach sind sie geschützt.

## LLM-Gateway (`llm_gateway/server.js`, `lib/install_llm_gateway.sh`)

Der n8n-Anthropic-Node v1.5 (unser Pin) kennt kein Prompt-Caching (v1.6 ab n8n 2.37 hat eine Option, bei uns aus); einziger Hebel ist die Credential-„Base URL". `inject_credentials.sh` setzt sie auf `http://127.0.0.1:8090` = dieser Dienst; er setzt die Cache-Haltepunkte und reicht unverändert an api.anthropic.com weiter. Kein OSS-Gateway setzt den Werkzeug-Haltepunkt für Anthropic direkt (LiteLLM nur System/Messages + Python-Lieferkette; Portkey/Envoy reichen `cache_control` nur durch) → eigener dependency-freier Node-Dienst.

- **Regel:** nur `POST /v1/messages` mit eigenem Werkzeug (`input_schema`) wird verändert: Haltepunkt am letzten Werkzeug + am System-Ende (`ttl` `LLM_GATEWAY_STATIC_TTL`, Standard 1h) + oberer automatischer (5 Min). Statische nur ohne eigene Block-Marker, oberer nur ohne eigenen oberen Marker. Nie den letzten Block markieren. Dieselben Anfragen bekommen `tool_choice` `{type:auto, disable_parallel_tool_use:true}` (nur bei fehlendem/`auto`-Wert): parallele `tool_use`-Blöcke einer Antwort kamen im n8n-Tools-Agenten (Node v1.5) mit leeren Argumenten beim Werkzeug an → Schema-Fehler, Wiederholungen bis `maxIterations`, Fehler statt Antwort (belegt 2026-10-23). Einmal-Aufrufe bleiben unverändert. Andere Pfade werden durchgereicht.
- **Ausfallsicher:** Body unlesbar/Einfügen wirft → Original-Bytes weiter; Anthropic-400 mit `cache_control` oder `tool_choice` → einmal ohne Einfügen wiederholen (`fallback:true`, doctor GELB); Upstream tot → 502 + fester Code.
- **Keep-Alive** (2026-10-23): nach jeder erfolgreichen Agenten-Anfrage merkt sich der Dienst je Anfang (Modell + Werkzeuge + System + Denk-Einstellungen) den Body ohne Gespräch + die Auth-Header (nur RAM, max. 16 Anfänge) und schickt ihn alle 55 Min mit `max_tokens: 0` an Anthropic (offizielles Pre-warming-Muster: nur Lesepreis statt erneutem 1h-Schreiben, gemessen ~0,19 $ je kaltem Finanz-Start). Fenster `LLM_GATEWAY_KEEPALIVE_HOURS` nach der letzten echten Nutzung (Standard 24, `0` = aus; Install-Env vor `core.env`); Fehler → Eintrag verworfen. Usage-Zeilen tragen `keepalive:true`; `/__health` zeigt `keepalive.on/hours/entries`.
- **Messung:** je Anfrage eine Zeile `{"ev":"usage",…}` auf stdout → Journal der Unit. Whitelist: Modell, Status, Dauer, `input_tokens`, `cache_creation_input_tokens` (+ 5m/1h-Split), `cache_read_input_tokens`, `output_tokens`, `web_search_requests` (Anthropic-Feldnamen statt OTel-GenAI). Prod-Blick: `journalctl -u lifeagents-llm-gateway`.
- **Betrieb:** Unit `lifeagents-llm-gateway` (`templates/lifeagents-llm-gateway.service.tpl`: `DynamicUser`, `ProtectSystem=strict`, `MemoryMax`, `Before=n8n.service`). `install_llm_gateway` läuft nach `install_n8n` und vor `inject_credentials`, kopiert `server.js` per `write_if_changed` nach `/usr/local/lib/lifeagents-llm-gateway/`, Neustart nur bei Änderung, prüft Port-Belegung. Bestands-Installationen wechseln beim nächsten `lifeagents update`. `doctor`: Unit + Health ROT. Test-Substrat: `enable_mock_llm.ps1` biegt den Upstream per Laufzeit-Drop-in um; Gratis-Test `scripts/dev/llm_gateway_test.ps1`.

## Gotchas — Fallgeschichten

- **Owner-Setup:** `N8N_INSTANCE_OWNER_MANAGED_BY_ENV` provisioniert den Owner nur beim allerersten Boot (n8n PR #27859) → Mint-401-Blocker; ersetzt durch `/rest/owner/setup`.
- **In-Memory-Trigger (Substrat-Probe 2026-10-19):** Zeitplan „jede Minute" aktiv → per `import:workflow` + `activate` auf „einmal im Jahr" umgestellt → weiter 2 Läufe in 130 s; derselbe Wechsel mit REST-`deactivate` vor dem Import → 0 Läufe. Die Webhook-Registrierung eines Telegram-Triggers macht n8n bei jedem Aktivieren neu (`checkExists`). Seit dem Update auf 2.44.4 (2026-10-20) laufen Abmelden/Aktivieren über `/unpublish`/`/publish` (seit n8n 2.33; `/activate`/`/deactivate` sind veraltet und fallen mit n8n 3 weg); das Neustart-Sicherheitsnetz bleibt.
- **gum-Proben-Rezept:** Wegwerf-Container `docker run --rm -v <repo>:/repo:ro -v <proben>:/probe:ro debian:12 bash /probe/<probe>.sh` (PowerShell: Befehle in eine Skript-Datei, nie inline `bash -c`); darin jq + gum (gepinnte Version/SHA aus common.sh nach `$LIFEAGENTS_LIB/bin`), `LIFEAGENTS_DIR`/`LIFEAGENTS_LIB`/`REPO_ROOT` setzen, die libs wie der `lifeagents.tpl`-Arm sourcen, Eingaben per `script -qec "<befehl>" /dev/null`. plain: `GUM_DISABLE=1 TERM=dumb`; gum: `TERM=xterm-256color`, Tasten verzögert senden (`( sleep N; printf '\r' ) | script …`; Esc `\x1b`, Pfeil runter `\x1b[B`) — gum verwirft beim Start gepufferte Eingaben; über den Windows-Bind-Mount ≥8 s je Taste. Der gum-Leerwert-Bug (`strings.TrimSpace` über die ganze Eingabe, `internal/stdin/stdin.go`) blieb unentdeckt, weil alle pty-Proben mit `GUM_DISABLE=1` liefen.
- **Dev-Ingress:** Befunde aus `TelegramTrigger.node.js` + `GenericFunctions.getSecretToken`: Produktiv-Route `<webhookId>/webhook` (POST auf `<webhookId>` → 404 „not registered"; Secret-Mismatch liefert 403); `secret_token` = `<workflowId>_<nodeId>` (im Repo build-stabil und damit öffentlich → `deploy_workflows` ersetzt Knoten-id + webhookId des Triggers je Instanz durch UUIDs aus `sha256(INGRESS_ID_KEY:Repo-id)`, Schlüssel einmalig in core.env, Security-Audit 2026-10); der Trigger aktiviert sich nur mit gültiger https-`WEBHOOK_URL` → Dev setzt `https://example.com/` (RFC 2606). Der Mock-Telegram-Server (`tests/mock_telegram/server.js` + `scripts/dev/enable_mock_telegram.ps1`) biegt den Telegram-`baseUrl` der Credential per REST-PATCH um und liefert die HITL-Resume-URL (n8n signiert nur über `pathname+search` → Host-Rewrite ist signatur-sicher).
- **`CREATE ON SCHEMA agent`:** in der Alt-Prod gehörte schema `agent` dem n8n-User; im Installer-Pfad legt `apply_schema.sh` als Superuser an → die n8n-Rolle bekam nur USAGE; der erste deterministische Agent-Test (Mock-LLM-Tier) deckte es auf.
- **`printf "\\echo"`:** ein doppelt-gequotetes `printf "\\echo '%s'"` wird zu Format `\echo …`, printf interpretiert `\e` als ESC → psql sieht `<ESC>cho` → `syntax error`; `\gset`/`\set`/`\if` sind harmlos, `\else`/`\endif` werden single-quoted emittiert. Latent bis zum Docker-Substrat (`db_test` nutzt den PowerShell-Treiber).

## Entscheidungen (bei uns anders — belegt)

- **`setMyCommands` ist ein Deploy-Zeit-Schritt** in `_wire_telegram` (Discord.js `deploy-commands`), kein Runtime-Workflow-Node und kein eigenes CLI-Verb; Command-SoT = Manifest-`commands`, Menü-Texte = Katalog `<pkg>.cmd.<name>` aus den getrackten `locales/*.json`; kein Hash-Guard (Single-User). **Je Sprache über `language_code`, nicht je Person** (Textkatalog Phase B): je Katalogsprache Default- und Owner-Chat-Menü mit `language_code`, dazu beide ohne in der Owner-Sprache — das Menü folgt der Telegram-App-Sprache. Ein Menü je Person müsste bei jedem Sprachwechsel/Pairing aus n8n gesetzt werden; n8n hat keine `setMyCommands`-Operation und das Telegram-Credential ist im HTTP-Node nicht nutzbar (kein `authenticate`) → Token im Workflow, verstößt gegen *Credentials & Privacy*. Test: `scripts/dev/bot_menu_test.ps1` (Mock speichert je Scope + Sprache, `LIFEAGENTS_TELEGRAM_API` biegt nur im Substrat auf den Mock).
- **Kein mengen-basiertes Prune** für Workflows/Credentials (kubectl ApplySet/Flux): n8n-Workflows tragen kein Ownership-Label; Fremd-API-Credential-Namen haben nicht einmal ein Paket-Präfix → explizite Tombstones.
- **Kein whiptail/dialog, gum nur optional:** unser Genre ist der lineare Bootstrap-Installer (rustup/Coolify/Hermes = printf); Alternate-Screen verdrängte Pairing-Code/Zugänge aus dem Scrollback. `gum choose` zeichnet inline.
- **Nacktes `lifeagents`/Sub-Nomen öffnet ein Verb-Menü** statt reiner Usage (gh/npm/kubectl = Hilfetext): die kommando-fluente Dev-/CI-Population existiert bei der Ein-Owner-Appliance nicht; Lizenz nur solange non-TTY byte-identisch bleibt, Args immer umgehen, ESC zur klassischen Usage. Kein Opt-in-Verb `menu`. Ein `ui_choose <header> <multi>` statt getrennter Select/MultiSelect. Abbruch = leerer stdout + `return 0`, kein Exit-Code (set-e-Kommandosubstitutions-Footgun). Kein Umbau auf „nur Labels an gum" (Copier-Stil); kein Runtime-`die` bei leerem Wert (verpufft in der Subshell) → Manifest-Lint 12e.
- **Keine Vorab-Frage „<Zugang> einrichten? [j/N]"** (Copier `when:`): Enter auf die erste Frage ist die Entscheidung. `value_prefix` flach statt Template-String. `package reconfigure` als eigenes Verb (nicht install-Re-Run, nicht unter `config`).
- **Kein `NONINTERACTIVE`/`CI`-Env-Schalter** (Homebrew): `--unattended` + „kein TTY" decken CI/Substrat; kein RFC-8628-Code-Alphabet (Deep-Link); kein `npm install --cache <tmp>`. DEFER → BACKLOG: Owner-chat_id zur Laufzeit statt eingebacken, QR-Code.
- **`TRUSTED_PROXIES` steuert Bind + Firewall** (bei HA/Gitea/Immich das X-Forwarded-For-Vertrauen; XFF regelt weiter `N8N_PROXY_HOPS=1`); kein `proxy refresh` (keine Namen gespeichert).
- **Caddy-Auto-Install verworfen** (6/6 Peers Immich/Gitea/Paperless/Vaultwarden/Miniflux/Uptime-Kuma sind document-only); kein Install-Wizard, kein `--no-caddy`; pure-A statt `--with-caddy`.
- **Paket-Zustand als materialisierte Projektion** (`installed_packages` + `/help`-Abschnitt) statt Laufzeit-Render-fn; `display_name` direkt deutsch + `summary`, kein `i18n.<locale>`-Block (Ein-Locale-Appliance).
- **Pflicht-Host-Key fehlt nicht-interaktiv:** `die` nur bei Erstinstallation; eine Bestandsinstanz hält das Update an (unattended-upgrades-Zurückhalte-Muster) — sonst legte ein Release mit neuem Pflicht-Key den Bot lahm. `lifeagents reconfigure` (Grundsystem) wendet per vollem Converge an (gitlab-ctl-reconfigure), weil Host-Keys abgeleiteten Zustand tragen. Re-Ask speichert erst nach der letzten Antwort (Mehr-Key-Credentials atomar). Host-Fragen bleiben eine Host-Tabelle (`_host_key_def`), kein Manifest-`credentials`-Block.
- **Backup:** Pivot von der In-DB-jsonb-Engine zu `pg_dump`/`gpg` (der Chat-Weg war der einzige Grund für In-DB-Krypto); Restore form-getrieben; Cross-Version nicht unterstützt (pg_restore/Borg/restic).
- **Gateway-Messung mit Anthropic-Feldnamen** statt OTel-GenAI (dort noch „Development").
- **`household` bündelt Personen-Lifecycle und Knocker-Blocking** unter einem Noun (lokales Mehr-Concern-pro-Noun-Muster wie `package`).

## n8n-Patches (`lib/n8n_patches.sh`)

- **Zweck:** bekannte n8n-Fehler korrigieren, bis n8n sie selbst ausliefert. Erster Eintrag `memory-all-tool-rounds` ([#41554](https://github.com/n8n-io/n8n/issues/41554)): Agent V3 `saveToMemory` schnitt die Tool-Runden einer Nachricht bis auf die letzte ab → der Bot vergaß eigene Writes (Owner-Fall 2026-10-23, Depot angelegt und danach geleugnet). Der Upstream-PR [#41577](https://github.com/n8n-io/n8n/pull/41577) (nur den Schnitt entfernen) reicht in 2.44.4 nicht: frühere Runden kommen über die Ausführungs-Metadaten serialisiert zurück (`{lc, kwargs}` statt `AIMessage`), die Postgres-Chat-Memory bricht dann mit `message.toDict is not a function` ab (im Substrat nachgewiesen) → zweite Stelle in `buildMessagesFromSteps` macht sie wieder zur `AIMessage`.
- **Ablauf:** `install_n8n` = `ensure_node` → `ensure_n8n_package` → `apply_n8n_patches` → `install_n8n_unit`, bei jedem Lauf (ein npm-Reinstall ersetzt die Datei). Je Patch-Zeile (`id|Pfad relativ zu npm root -g|sha256 Original|sha256 gepatcht|Grund`) entscheidet `n8n_patch_status`: `original` → jedes Ersatz-Paar aus `_n8n_patch_pairs` wörtlich anwenden (node, je Anker genau ein Vorkommen), Ergebnis-sha256 prüfen, `<datei>.orig` behalten, `N8N_PATCH_CHANGED=1` → Neustart; `patched` → no-op; `changed` (Leit-Anker fehlt, vermutlich von n8n behoben) / `unknown` / `missing` → nichts anfassen, `warn`, nie fatal. doctor: `patched` grün, `changed` Hinweis, sonst ROT.
- **Pin-Wechsel:** neue Fassung hashen (`sha256sum` im Substrat) und eintragen, oder den Patch löschen, wenn n8n den Fehler behoben hat (BACKLOG-Trigger). Der Substrat-Basisimage-Bau (`build_base.sh`) installiert n8n ungepatcht, `provision.sh` patcht → jeder `-Reset` testet den Patch-Zweig.
- **Entscheidung (arch-challenge 2026-10-23):** patch-package/`pnpm patch`/npm `overrides` setzen ein eigenes Projekt-Manifest voraus (n8n läuft npm-global), ein Fork oder der Community-Ersatz-Agent ([better-ai-agent](https://github.com/fjrdomingues/n8n-nodes-better-ai-agent), seit 2025 ungepflegt, eigener Node-Typ) kostet mehr als er nützt → verankerter Ersatz mit Fingerabdruck der ganzen Datei (Muster Ansible `replace`; strenger als Diff-Kontext, kein Zusatzpaket `patch`).
