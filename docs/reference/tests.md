## Flakiness-Mechanik

- **Execution-Korrelation: monotone Exec-id.** Vor dem Feuern liest der Treiber die höchste Execution-id des Ziel-Workflows (`Get-MaxExecId`); die danach neu erscheinende Execution ist der Lauf des Cases. Der frühere `subExecution.executionId`-Pfad (Harness `Run Info` + `responseMode=lastNode`) ist abgelöst — die am HITL-Gate suspendierte Execution liefert keine Run-Info-`subExecution`-Metadata mehr.
- **read_tools kann unvollständig sein:** der n8n-Action-Log (`metadata.subNodeExecutionData.actions`) erfasst nicht jeden Read-Call (real: `load_context` fehlte trotz nachweislich genutztem Plan-Inhalt).
- **Memory-Clear:** die Tiers leeren per-Case in der n8n-Container-DB über `Clear-ChatSessionMemory` (`scripts/dev/test_n8n_state.ps1`): findet alle `agent.*_chat_memory`-Tabellen über `pg_tables` (entstehen lazy beim ersten Agent-Turn) und löscht genau die Session des Cases — Agent-Tiers die des gepairten Owners, `orch_test`/`multiturn_test` die numerische aus `Get-TestChatId`, E2E die `test_e2e…`-chat_id (multiturn: einmal je Case). Stale Test-Memory ließ den Advisor real alte Antworten zusammenfassen (leere read_tools → falsche Judge-FAILs).
- **tc16 (book_stock_sell) — quarantäniert.** Root-Causes adressiert: die Tool-Description trennt den Lookup eindeutig (holding_id nur aus `finance_depot_holdings_overview`, nie aus Sells); `holding_id`-`$fromAI`-Typ `number`→`string`. Rest: gelegentlicher Timeout. Korrektheit voll abgedeckt via `test_fn_book_stock_sell.sql` + `e2e05`. Re-Evaluieren: bei ≥5 stabilen isolierten Läufen `quarantined` entfernen.
- **Mutation-Spot-Check (optional):** in einer `fn_book_*` ein Vorzeichen/Grenzwert mutieren, `db_apply` + Test → muss rot werden; dann `git checkout` + `db_apply` → grün. Einmalig verifiziert an `fn_book_transaction`.

## Harness-Mechanik (Layer 2 + 3)

Die n8n Public-API kann Workflows nicht ausführen. Jeder Test läuft über einen separaten Harness-Workflow (Webhook + Header-Auth → `Execute Workflow` → Ziel → `Run Info`). Generator: `scripts/build/build.ps1` (Harness-Engine `scripts/build/lib/harness.ps1`, Paket-Einträge `packages/*/build/workflows/harnesses.ps1`); die Harnesses sind getrackt und werden mit dem Baum ins Substrat deployt. `responseMode=lastNode`: der Webhook-POST blockiert bis Lauf-Ende und liefert `{harness_execution_id}`; alle Harness-Skripte setzen am POST ein festes `-TimeoutSec 8` und behandeln einen POST-Timeout als „weiter per Polling". **Fixture-Pre-Flight** (`n8n_test.ps1`, Default-Suite): prüft, dass die von `finance_cases.json` referenzierten Entitäten existieren — sonst Abbruch mit Seed-Hinweis statt ~23 False-FAILs; delegiert an `scripts/test_fixtures.ps1 -Verify`. Seed: `tests/fixtures/util_seed_test_fixtures.sql`.

**Gate-Auflösung über Mock-Telegram (kein Bypass):** das HITL-Gate hat keinen `test_`-Bypass — jede Bestätigung läuft durch das echte Telegram-Send-and-Wait. Die Tiers feuern mit numerischer `chat_id` (Routing/Multi-Turn) bzw. `test_e2e`-`chat_id` (E2E, nur für den Advisor/Monitor-Sentinel-Domain-Switch) und lösen das Gate über das abgefangene Mock-Telegram + die signierte Resume-URL auf: decline (Routing-Tiers → Tool nimmt `cancelled`) bzw. approve (E2E → Write läuft echt). Mechanik `Wait-ExecResolvingGates` (`scripts/dev/test_n8n_state.ps1`); `hitl_gate_test.ps1` beweist Approve+Decline.

**Tool-Detection-Pfad (`n8n_test.ps1`):** `runData[<Agent-Node>].metadata.subNodeExecutionData.actions[].action.nodeName`; Write-Tools via `$nn -like 'tool_*'`; Read-Tools als `read_tools`-String im Judge-Bundle. `orch_test.ps1` prüft `Call 'agent.finance'` in `runData['Orchestrator agent']`. `infra_test.ps1` prüft must_be_nonempty / must_contain / must_not_contain / must_equal im Check-Node. **Per-Case-Timeout** `"timeout_s": 240` überschreibt den `-Timeout`-Default (bei Multi-Turn je Turn) = die Polling-Frist (`Wait-ExecResolvingGates -TimeoutSec`); der POST selbst wartet fest 8 s. Poll-Intervall 1 s.

**PASS/FAIL-Semantik (`n8n_test.ps1`):** `expected_tool` gesetzt → PASS wenn genau dieser `tool_*` im runData steht (auch wenn das Tool danach `cancelled` liefert); `expected_tool=null` → PASS wenn kein `tool_*` aufgerufen wurde. **`expected_tool_args`** `{ feld: wert, … }`: ist es gesetzt und das Routing stimmt, prüft das Skript die Argumente gegen `action.input` — Teil des det-Gates. Matching (`Compare-ArgValue`): Zahlen numerisch (Epsilon `0.0001`), Strings case-insensitiv + Substring-tolerant, gemischt → kein Match. Dynamische Werte (aufgelöste IDs) nicht asserten.

**Hybrid mit LLM-Judge:** Cases mit `expected_behavior` werden deterministisch gecheckt und in `judge_bundle.json` geschrieben (`task`, `expected_behavior`, `expected_tool`, `det_pass`, `actual_tool`, `actual_tool_input`, `read_tools`, `actual_output`). `judge_eval.ps1` bewertet per Claude Haiku 5.5 (Structured Output `verdict`/`reason`, Denk-Tiefe low; `ANTHROPIC_API_KEY` in `.env`, Key per `x-api-key`-Header): `OVERALL PASS` nur wenn `det_pass=true` und Judge=`PASS`. Die eigentliche Entscheidung steht oft in `actual_tool_input`, nicht im Antworttext.

## E2E-Tier (Tier 5)

Schließt die „Mock-Falle" des Routing-Tiers (der lehnt jeden Write ab). Das echte Gate wird approved (`Wait-ExecResolvingGates -Approve $true`) → der Write läuft echt durch `agent.fn_*`; `e2e_test.ps1` verifiziert per `verify_sql` (Skalar == `expect`). Optionales Case-Feld `setup_sql`: läuft nach dem Cleanup mit dem paketneutralen Prelude-Helfer `pg_temp.ok(label, res)` (macht `{ok:false}` hart) und legt die Voraussetzungen per `<pkg>.fn_*` an (ids per Subselect im Case, das Skript kennt kein Paket); nur einfache Hochkommas (doppelte gehen in der `docker exec`-Übergabe unter PS 5.1 verloren). C4: auch positive Fälle müssen `status=success` enden. Multi-Step-Sequenzen laufen in einer Execution durch. Cleanup `agent.fn_clear_e2e_data()`: Pre-Assertion „jede Lösch-ID trägt den Marker" + Runaway-Obergrenze, Post-Assertion „keine Sentinel-Zeile bleibt"; FK-sicher; atomar; Paket-Teile im Konventions-Hook `<pkg>.fn_clear_e2e_data(text)`. Cleanup-Zeitpunkte: vor jedem Case und im `finally` (fängt keinen harten Kill). Negativ-Case: nicht existierende Entität → `fn_resolve_*` 0 Treffer → `ok:false`, `verify_sql` asserted 0 Sentinel-Zeilen. Upgrade-Pfad für parallele Läufe: Run-ID im Marker (`__E2E_<runid>__`) — Backlog.

## Golden-Cases — Hintergrund

Der Routing-Tier läuft nicht in einer Transaktion (kein Rollback, keine Wegwerf-Fixture) und der Agent löst Entitäten via `postgres_select` gegen die Live-DB auf → ein `set_*`/`close_*`/`delete_*`-Golden ohne dauerhafte Prod-Entität FAILt als Fixture-Defekt, nicht als Tool-Defekt. Abdeckung stattdessen über DB-Test (`test_fn_*`, beide Zweige + Guards) und E2E (Entität im selben Case anlegen → close/delete → `verify_sql` → Cleanup). `chat_id` je Case: Agent-Tiers feuern als gepairter Fixture-Owner (numerisch), `orch_test`/`multiturn_test` mit numerischer chat_id je Case-id (`Get-TestChatId -Seed $tc.id`); das `chat_id`-Feld in den `*_cases.json` ist für die Routing-Tiers nur Doku, E2E nutzt es; `infra_cases.json` feuert direkt am Harness ohne Sender-Gate.
