# Provisioning-Kern — Konventionen (lädt beim Arbeiten in `provisioning/`)

Der Auslieferungs-Kern (bash + ein Node-Dienst, der LLM-Gateway) läuft auf Debian 12, byte-identisch für Dev/Test (ephemerer systemd-Docker-Container via `scripts/dev/bootstrap_test_n8n.ps1`) und Release (Proxmox-LXC, `curl|bash`). PowerShell bleibt die Autoren-Werkzeugkette (`build.ps1`, `db_apply`), bash die Auslieferungs-Werkzeugkette; beide lesen dieselben getrackten Artefakte. Mechanik aller Schritte, Install-UX-Details, Runtime-CLI, Fallgeschichten und Entscheidungen → `docs/reference/provisioning.md` (on-demand). Paket-Vertrag → `docs/package-contract.md`.

## Struktur

- `install.sh` = Wegwerf-Bootstrap-Launcher (self-contained, kein lib-Sourcing; `set -euo pipefail`; resolve/fetch/verify/delegate → `exec provision.sh`); wird **nie** in die Runtime gespiegelt. `provision.sh` = interner Applier (`main()` = die Install-Schritte + Uninstall + `install_cli`; kein Fetch/`--version`, kein Endnutzer-Einstieg). `doctor.sh` = standalone Diagnose. `llm_gateway/server.js` = der eine Nicht-bash-Baustein (dependency-frei).
- `lib/*.sh` werden **gesourct** (kein Shebang, kein `set -e`): common, preflight, packages, `install_*`, firewall, `*_cli`, apply_schema, seed_data, bootstrap_owner, inject_credentials, deploy_workflows, release_inputs, uninstall, `pkg_*`, backup_cli, upgrade_guard; `fetch_release.sh` nur Runtime (`lifeagents update`/`reconfigure`), nie von `provision.sh`.
- `templates/` (`@@KEY@@`-Platzhalter): `n8n.env.tpl`, `n8n.service.tpl`, `lifeagents-llm-gateway.service.tpl`, `Caddyfile.tpl` (nur ausgegeben, nie installiert), Firewall-Templates, `lifeagents.tpl`. `.github/workflows/release.yml` baut das Release-Asset per `git archive` (Pathspec = eine Quelle, `layout_lint` L6).

## Harte Regeln (bash-Kern)

- **`set -euo pipefail` nur im Top-Script** (`install.sh`/`provision.sh`/`doctor.sh`/`lifeagents`); `lib/*.sh` erben den Error-Mode, setzen ihn nie selbst.
- **Idempotenz, Zweitlauf = no-op:** jeder Schritt guarded (`add_apt_key`/`add_apt_source`/`write_if_changed`, `dpkg -s`, `pg_roles`/`pg_database`-EXISTS); systemd-Reload/Restart nur bei echter Datei-Änderung (`write_if_changed` rc0 → `enable_start_unit … 0`).
- **`N8N_ENCRYPTION_KEY` wird einmal erzeugt und nie überschrieben** (`prepare_n8n_env` liest die bestehende Env zuerst); analog DB-Passwort. Secrets = `rand_hex`. `core.backup_key` nie rotieren.
- **Secrets nie im Repo, nie im argv:** nur `/etc/n8n/n8n.env` (640 root:n8n) bzw. `/etc/lifeagents/<pkg>.env`; First-Init-Overrides aus Prozess-Env. HTTP mit Secrets nur über `curl_secret` (`curl -K -`) bzw. `n8n_api_curl`/`tg_api_curl` (`/proc/<pid>/cmdline` ist für jeden lesbar).
- **Templates statt Heredocs** (`render_template <tpl> KEY=VAL …`); Werte sind Hex/Codenames/Pfade.
- **UTF-8 ist Gesetz, egal was das System sagt:** Top-Scripts exportieren `LANG/LC_ALL=C.UTF-8`; `postgresql-common` legt den Cluster mit der **System**-Locale aus `/etc/default/locale` an (nicht der Sitzung; Proxmox-Vorlagen: `LANG="C"` → SQL_ASCII, v0.4.0-Abbruch) → Drop-in `createcluster.d/lifeagents-utf8.conf` vor dem Paket-Install, App-DB per `createdb -E UTF8 --locale=C.UTF-8 -T template0`, `require_utf8_db` bricht bei einer Nicht-UTF8-DB ab (schon im Preflight, vor `upgrade_prepare`). Durchgesetzt von `contract_lint` 20 (statisch, auch Test-DBs), doctor, Substrat (`LANG="C"` + harter Check); `test_db_encoding.sql` hält die db_test-DB auf Prod-Parität (UTF8 + C.UTF-8).
- **Doctor read-only**, Exit = Anzahl ROT; der Ingress-Check misst das Outcome (Trigger aktiv + HTTPS erreichbar), nicht welcher Proxy läuft. Proxy-Allowlist → Root-`CLAUDE.md` *Telegram-Architektur*.
- Skripte stets per `bash "<script>"` rufen (Exec-Bit-unabhängig, Win-authored). `provisioning/** text eol=lf` in `.gitattributes` — neue Dateien LF.

## Install-Ablauf (Regeln je Schritt)

- **Owner-Bootstrap** (`bootstrap_owner.sh`, nach `apply_schema`, vor dem API-Key-gegateten Deploy): Owner-Setup über n8ns `/rest/owner/setup`-Flow (nicht `N8N_INSTANCE_OWNER_MANAGED_BY_ENV`); `N8N_API_KEY` override-first, per-Key-Upsert in `/etc/lifeagents/core.env`. Host-RO-Rollen (`core_ro`/`context_ro`) werden hier gemintet, Paket-Rollen erst in `pkg_install_one`. **Den produktiven `setWebhook` setzt n8n selbst** beim Aktivieren des Telegram-Triggers — ein manueller Aufruf würde überschrieben. Owner-Skelett muss vor dem Pairing existieren; Pairing-Code nur im Terminal, nie über Telegram; unattended wird nie ein Code armiert.
- **Schema + Workflows + Credentials:** `apply_schema.sh` fährt das Flyway-3-Phasen-Modell (+ util) als Superuser in einer psql-Session (`.claude/rules/sql.md` *Migrations-Modell*). Credential-Upsert ist **id-stabil und fail-closed** (bestehende id per `GET /credentials` name+type; ein GET-Fehlschlag bricht ab; Secrets werden nie adoptiert), jede Credential wird nach dem Import per `/credentials/{id}/test` sofort validiert. `deploy_workflows.sh` nutzt `import:workflow` (id-erhaltend, nie REST-POST) **nur für neue/geänderte Workflows** (Fingerabdruck + Live-versionId-Abgleich, im Zweifel alle; Mechanik → Referenz), **meldet laufende Auslöser per REST-`unpublish` (bis n8n 2.32 `deactivate`) vor dem Import ab** (sonst liefe ein geänderter Zeitplan doppelt; kein Deploy-Restart mehr), aktiviert alle per Fixpunkt; Rest-Platzhalter `__CFG_*` → `die` bevor live etwas geändert wird. Stillgelegte Workflows/Credentials nur über explizite Manifest-Tombstones (`retired_workflows`/`retired_credentials`), nie Prune.
- **Daten-Seed** (`seed_data.sh`): `ai_models` zuerst, dann `.config`-Blöcke aller Manifeste, Katalog, Contexts, dann die paket-generischen Registry-Seeder. Seed enthält **keine PII**; Onboarding-Contexts (`family`/`finance_profile`/…) werden nie geseedet. Conffile-Guard `managed_by <> 'agent'`: vom Owner/Agenten übernommene Zeilen überschreibt ein Re-Seed nie. `packages/*/contexts/**.md` sind LF-gepinnt (roh gelesen).

## Install-UX (Regeln)

- **Eingabe nur über die sanktionierten Primitive** `ui_input`/`ui_choose`/`ui_wait_key` (`contract_lint` 12d); `ui_choose`-Vertrag: leer + `return 0` = Abbruch/kein TTY, Strg-C = `ui_abort`; ein leerer Wert heißt „nichts gewählt". gum ist optional und nie fatal; **unattended/kein TTY = immer plain** (deterministische Substrat-Ausgabe). `ui_wait_key` nie per `$(...)`.
- **Quiet-Modus:** `ui_box` und Recap gehen nur auf fd3, nie ins Log (Pairing-Code, Passwörter); `--verbose`/non-TTY = volle Ausgabe.
- **Fragen vorab** (`collect_release_inputs` → `collect_package_inputs`), Seen-Gate (`KEY=`-Zeile = schon gefragt); Pflicht-Host-Keys (`_REQUIRED_HOST_KEYS`: Name, Geburtsdatum, Telegram-Token, Anthropic) haben interaktiv kein Seen-Gate. **Fehlt ein Pflicht-Key nicht-interaktiv:** Erstinstallation `die`, Bestand hält das Update an (`exit 0` + Telegram). Live-Checks nur für Neu-Eingaben; 3× ungültig wird nie still übernommen.
- **Install-UX-Phase 5:** `TRUSTED_PROXIES` ist der eine Fakt (core.env); n8n-Bind und nft-Freigabe sind abgeleitet, nie separat gespeichert. **Firewall fail-closed:** n8n lauscht nur dann auf 0.0.0.0, wenn die Tabelle `inet lifeagents` nachweislich geladen ist. Mechanik im Kopf von `lib/firewall.sh`.
- **Install-UX-Phase 6/7:** Begrüßung erst nach `_oc_finalize` (vorher steht die Owner-chat_id in den Workflows auf 0); Paket-Zustand aus genau einer Regel (`_pkg_state_rows`, Registry). `_is_first_install` = VERSION-Marker fehlt. Re-Ask (`reask=1`) speichert erst nach der letzten Antwort; Esc in der Übersicht = Abbrechen, nichts installiert. `lifeagents reconfigure core` wendet per vollem Converge an.
- `--profile` steuert nur Netzwerk/Ingress; `--unattended <env-file>` ist der nicht-interaktive Modus (Pfad Pflicht); `--yes` ist nicht `--unattended`. `INSTALL_PROFILE` persistiert in core.env, ebenso `HOUSEHOLD_TIMEZONE` (Standard Berlin, nie die Container-Zeitzone; daraus n8n-Zeitpläne und die DB-Sitzungs-Zeitzone für „heute“, Mechanik → `docs/reference/provisioning.md`).
- **Bootstrap-Launcher:** `install.sh` prüft SHA256 vor dem Entpacken; `fetch_release.sh` ruft nie `install.sh`; Download immer anonym aus dem öffentlichen Repo (kein Token, keine Frage; Download-Block in beiden byte-gleich, `contract_lint` 23). Release-Asset = nur getrackte Dateien (`git archive`).

## Update im Chat + Release-Signatur

- **Brücke n8n → root = Daten-Zeile, nie Datei/sudo:** der Tap endet über die Callback-Registry in `core.update_requests`, der root-Timer `lifeagents-update-run` übernimmt sie (`flock` + `core.fn_update_request_claim`). Bei uns anders als `.path`-Unit + Spool-Datei (arch-challenge 2026-10-24): der Tap landet ohnehin in der DB, eine Datei bräuchte den ersten Datei-Node in n8n. Der Runner traut der Zeile nicht (installiert nur `releases/latest` > `VERSION`). Mechanik → Referenz *Update im Chat*.
- **Runner-Units:** keine Abhängigkeit auf `n8n.service`; ein Re-Provision startet nur die Timer neu, nie den laufenden Runner-Service (er führt genau dieses Update aus).
- **Ergebnis statt Exit-Code:** neue Abbruchstellen mit festem Grund → `die_because <code>`; neuer Schritt in `provision.sh main` → `ui_step <text> <stage>` (+ Key `core.update.stage.<code>` und CASE in `core.fn_update_report`). `die` zählt nur in der Haupt-Shell als gescheitertes Update.
- **Release-Schlüsselbund** `/etc/lifeagents/release-signing.gpg`: einmal anlegen, nie durch ein Update überschreiben; die Prüfung lebt im gespiegelten gh-download-Block (`_release_fetch_verify`). Schlüssel nur über `scripts/new_release_key.ps1` (contract_lint 24).

## Backup/Restore

- Nur die Nutzerdaten-Teilmenge aus dem Manifest-`backup`-Block; `pg_dump` ignoriert `-n`, sobald `-t` gesetzt ist. Restore ist atomar (eine `psql -1`-TX); Entschlüsselung, Pre-Flight und Version-Gate laufen vor dem Wipe; Cross-Version bewusst nicht unterstützt.

## LLM-Gateway

- Inhalte gehen nur an api.anthropic.com (Privacy-Hard-Rule; externe Gateways ausgeschlossen). Nie Header, Schlüssel oder Inhalte loggen; Fehler nur als feste Codes. Die n8n-Built-in-Cache-Option auch nach einem Update aus lassen (setzt nur den oberen Haltepunkt). `install_llm_gateway` bricht ab, **bevor** die Credential umgestellt wird, wenn `/__health` nicht antwortet.
- Keep-Alive hält Anfang + Auth-Header nur im RAM (nie Gespräch, nie Platte); Schalter `LLM_GATEWAY_KEEPALIVE_HOURS` (Install-Env vor `core.env`, Standard 24, `0` = aus). Das Test-Substrat setzt `0` (`bootstrap_test_n8n.ps1`), sonst stupst ein liegengelassenes Substrat den Cache auf dem Entwickler-Schlüssel an.

## Gotchas

- **Owner-Setup:** `N8N_SECURE_COOKIE=false` Pflicht (UI/REST nur über localhost-http); Owner-Email muss FQDN sein + Passwort-Policy 8–64/≥1 Ziffer/≥1 Großbuchstabe; API-Key braucht `scopes` (erst `GET /rest/api-keys/scopes`).
- **Credential-`data`-Validator:** `postgres` braucht `sshTunnel:false`; `googlePalmApi`/`httpHeaderAuth` brauchen `allowedDomains:""`; `anthropicApi` `headerName/headerValue/allowedDomains`.
- **publish-Modell:** `executeWorkflow`-Ziele müssen vor dem Referrer published sein → Fixpunkt-Pässe (`deploy_workflows`).
- **In-Memory-Trigger:** `import:workflow` meldet einen laufenden Auslöser nicht ab → REST-`unpublish` vor dem Import (Deploy; schadet auch unter dem 2.40-Veröffentlichungs-Dienst nicht); ein Paket-Uninstall löscht Workflows wirklich → `pkg_teardown.sh` startet n8n einmal neu.
- **gum `choose` verschluckt ein leeres Label** (`TrimSpace` über die ganze Eingabe) → `_UI_EMPTY_VALUE`; Picker-Änderungen immer auch mit gum proben, nicht nur `GUM_DISABLE=1` (Rezept → Referenz).
- **`[ -r /dev/tty ]` ist kein TTY-Test** (crw-rw-rw-, ENXIO beim Zugriff) → `tty_usable`.
- **Dev-Ingress:** Route `<webhookId>/webhook` (nicht blosser `<webhookId>`); Secret-Fehler = 403, nicht 404; `secret_token` = `<wfId>_<nodeId>`; der Trigger aktiviert sich nur mit https-`WEBHOOK_URL` (Dev: `https://example.com/`).
- **Pairing-Pre-Router braucht `core_ro`** (Credential `Postgres core_ro (read-only)`; `finance_ro` wäre für `agent.*` permission-denied).
- **n8n-Rolle braucht `CREATE ON SCHEMA agent`:** der Chat-Memory-Node legt `agent.<agent>_chat_memory` zur Laufzeit an (`apply_schema.sh` Phase 4 grantet es; nur agent).
- **Node = genau `NODE_MAJOR`** (`_node_ok`; ungerade Node brechen `isolated-vm`); n8n-Binary-Pfad aus `command -v n8n`, nie hartkodiert; `postgresql-<PG_VERSION>` bleibt per `apt-mark hold` gehalten (kein PG-Neustart von außen unter laufendem n8n), `install_postgres` löst ihn nur kurz für `--only-upgrade` (Sicherheits-Minors) und hält wieder; `pg_isready`-Warteschleife nach Erstinstall.
- **`npm warn install-scripts` beim n8n-Install ist nur ein Hinweis:** npm 11 (Node 24) führt ungeprüfte Install-Skripte trotzdem aus (Arborist überspringt nur `allowScripts`-Verbote; `isolated-vm` lädt aus `prebuilds/`, daher kein `out/`) → bewusst stehen lassen. npm 12 blockiert sie, kommt laut Node-Release-WG aber nicht nach Node 22/24/26 ([nodejs/Release#1161](https://github.com/nodejs/Release/issues/1161)); ein `NODE_MAJOR`-Sprung auf npm 12 braucht `--allow-scripts=<liste>` in `ensure_n8n_package` (auch im `npm rebuild`-Zweig).
- **Versionswechsel = erst sichern, dann tauschen** (`lib/upgrade_guard.sh`, Ablauf + Rückweg → Referenz *Versionswechsel*); auf n8n immer über `/healthz/readiness` warten (`/healthz` ist grün, bevor die Migrationen fertig sind). Seit 2.4x lehnt `DELETE /workflows/{id}` einen veröffentlichten Workflow ab → `n8n_delete_workflow` unpublisht vorher; 2.44.4 meldet `unpublish` 200, bevor die Abmeldung fertig ist (DELETE = 409 „still being unpublished") → 409 wird wiederholt. Ein `nftables`-Neustart startet n8n per `Requires=` mit (~10 s bis readiness).
- **`printf "\\echo …"` macht aus `\e` ein ESC** → psql-Syntaxfehler; Meta-Befehle als `%s`-Argument drucken (`printf '%s\n' "\\echo '…'"`).
- **n8n-Pin-Wechsel ⟹ `lib/n8n_patches.sh` prüfen:** je Patch die Original-/Ziel-sha256 der neuen Fassung eintragen oder den Patch löschen (n8n hat behoben); sonst lässt der Installer die Datei unangetastet und doctor meldet ROT. Mechanik → Referenz *n8n-Patches*.

## Verifikation

- Lokal: `bash -n` aller Skripte + CRLF-Check + Helfer-Smoke. **Volle Abnahme = der byte-identische `provision.sh` im ephemeren systemd-Container von null** (`scripts/dev/bootstrap_test_n8n.ps1 -Reset -Cold`, `jrei/systemd-debian:12`; der Default-`-Reset` startet aus einem Basis-Image mit vorinstallierter Software und testet die Erstinstallations-Zweige nicht; CI `genericity` fährt kalt) → `doctor.sh` grün, `infra_test` grün, Zweitlauf no-op; der Bootstrap-Launcher separat per `bootstrap_test_n8n.ps1 -Version <tag>`. Prod = Proxmox-LXC, derselbe `provision.sh` → kein Drift.
